2. Create src/lib/r2.ts with three functions:
- `uploadDashboardHtml(slug: string, html: string): Promise<void>` -- uses `getCloudflareContext()` to get the DASHBOARDS R2 binding, calls `bucket.put("d/{slug}.html", html, { httpMetadata: { contentType: "text/html; charset=utf-8" } })`
- `getDashboardHtml(slug: string): Promise<ReadableStream | null>` -- calls `bucket.get("d/{slug}.html")`, returns `object?.body ?? null`
- `deleteDashboardHtml(slug: string): Promise<void>` -- calls `bucket.delete("d/{slug}.html")`

3. Create src/lib/publish.ts with two functions:
- `buildConfigFromDashboard(dashboard: DashboardWithData): AnyDashboardConfig` -- Maps Supabase data to CONFIG shape. For sell dashboards: extract all sell_data fields into the CONFIG structure the template expects (comps, market_metrics, property details, narratives, etc.). For buyer dashboards: map buy_data fields. For buysell: merge both. Use extractConfig() on existing generated dashboards as reference for the expected CONFIG shape. The key insight from research: CONFIG is the same shape the generation pipeline produces, so map DB fields directly to CONFIG keys.
- `renderDashboardHtml(dashboardId: string): Promise<string>` -- calls getDashboard(dashboardId), determines template type from dashboard.type (map "sell" -> "sell", "buyer" -> "buyer", "buysell" -> "buysell"), calls getTemplateHtml(type), calls buildConfigFromDashboard(dashboard), returns injectConfig(template, config).

4. Create src/lib/__tests__/r2.test.ts -- Mock getCloudflareContext to return a fake R2Bucket with put/get/delete methods. Test all three r2.ts functions verify correct key format and method calls.

5. Create src/lib/__tests__/publish.test.ts -- Mock getDashboard, getTemplateHtml, injectConfig. Test buildConfigFromDashboard produces expected CONFIG shape from a sample DashboardWithData. Test renderDashboardHtml chains the calls correctly.

IMPORTANT: For buildConfigFromDashboard, study the existing template CONFIG structure by examining one of the template HTML files (e.g., template-sell.html) to understand what CONFIG keys the template expects. The function must produce a CONFIG object that matches the template's expectations. Key fields typically include: clientName, agentName, address, beds, baths, sqft, estimatedPrice, comps array, marketSnapshot, pricingStrategy, propertyHighlights, prepItems, timeline, etc.

1. Create src/app/api/dashboard/[id]/publish/route.ts:
- POST handler: authenticate via createClient (server), call renderDashboardHtml(params.id) to get HTML string, call uploadDashboardHtml(dashboard.slug, html) to upload to R2, then call updateDashboard(params.id, { status: "published", published_at: new Date().toISOString() }) to update status. Return JSON: `{ url: "/d/{slug}", slug: dashboard.slug, published_at: timestamp }`. Wrap in try/catch, return 500 on error.
- Server-side slug lock enforcement: if dashboard already has published_at set, ensure slug cannot change (the R2 key uses the existing slug).

2. Create src/app/api/dashboard/[id]/download/route.ts:
- GET handler: call renderDashboardHtml(params.id) to get HTML, get dashboard via getDashboard(params.id) for the slug. Return `new Response(html, { headers: { "content-type": "text/html; charset=utf-8", "content-disposition": 'attachment; filename="{slug}.html"' } })`.

3. Create src/app/d/[slug]/route.ts:
- GET handler: this is a public route (middleware already whitelists /d/). Call getDashboardHtml(params.slug) to get ReadableStream from R2. If null, return 404 Response. If found, return `new Response(body, { headers: { "content-type": "text/html; charset=utf-8", "cache-control": "public, max-age=60" } })`. Stream the body directly -- do NOT call .text() first (templates are ~788KB, streaming avoids memory issues).

All three routes use the patterns from 03-RESEARCH.md. Import from @/lib/r2 and @/lib/publish.
